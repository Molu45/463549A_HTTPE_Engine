## 1. Idempotency Key Semantics & Enforcement Strategy

To prevent accidental double charges caused by client network retries or gateway timeouts:
1. **Mandatory Header:** Every mutating request (`POST /v1/payments`) requires an `Idempotency-Key` header containing a UUIDv7 identifier generated by the caller.
2. **Lifecycle:** Idempotency keys are cached in the Redis Cluster with a strict **24-hour Time-To-Live (TTL)**.
3. **Status Flow:**
   - On first arrival, Redis sets `idempotency:{key}` to `IN_FLIGHT` using `SETNX`.
   - If an identical request arrives while `IN_FLIGHT`, the API Gateway immediately rejects it with `409 Conflict`.
   - Once the transaction completes, Redis stores the terminal JSON payload with `status: COMPLETED`. Subsequent retries receive the cached `200 OK` response without mutating account balances.

## 2. Rate-Limiting & Traffic Shaping Strategy

Kong API Gateway enforces rate limiting using the **Redis-backed Token Bucket algorithm** to defend downstream databases against burst over-saturation:
+-------------------------------------------------------------------------------------------------+
| RATE LIMITING TIER ALLOCATION                                                                   |
+-------------------+--------------------+--------------------+-----------------------------------+
| Client Tier       | Sustained Rate     | Burst Bucket Size  | HTTP Headers Returned             |
+-------------------+--------------------+--------------------+-----------------------------------+
| Standard User     | 10 req / sec       | 25 requests        | X-RateLimit-Limit, Remaining,     |
| Premium Merchant  | 500 req / sec      | 1,500 requests     | X-RateLimit-Reset                 |
| Enterprise Switch | 3,000 req / sec    | 6,000 requests     | Retry-After: seconds (on 429)     |
+-------------------+--------------------+--------------------+-----------------------------------+


When a client depletes their token bucket:
- The gateway immediately short-circuits execution and responds with `HTTP 429 Too Many Requests`.
- The response includes the `Retry-After: <seconds>` header to direct client backoff timers.

## 3. Standardized Error Response Model

All API endpoints strictly adhere to RFC 7807 Problem Details representation:

```json
{
  "error_code": "ERR_CONCURRENT_VERSION_CONFLICT",
  "message": "The account version changed concurrently. Request has been retried.",
  "timestamp": "2026-09-15T12:00:00.000Z",
  "trace_id": "c61b2a9d-045a-4e2a-88f1-34582f3491ba"
}
+-------------------------------------------------------------------------------------------------+
| CORE ERROR CODE DICTIONARY                                                                      |
+-------------------------------+-------------+---------------------------------------------------+
| Error Code                    | HTTP Status | Trigger Condition                                 |
+-------------------------------+-------------+---------------------------------------------------+
| ERR_IDEMPOTENCY_KEY_MISSING   | 400         | Required Idempotency-Key header is absent         |
| ERR_INSUFFICIENT_FUNDS        | 400         | Available balance < requested debit amount        |

4. API Versioning & Backward Compatibility
Path-Based Versioning: All external endpoints are prefixed with the major version (e.g., /v1/payments).

Deprecation Policy: Deprecated fields and endpoints return an HTTP Deprecation: true header and remain active for a minimum of 180 days prior to retirement.
